HEWGE / AUTHENTICITY & OWNERSHIP
Scope
This runbook owns physical-piece authentication, tag provisioning, commissioning and replacement. Use docs/permanent-provenance.txt for ownership registration, fee/refund approval and recovery of the ledger; docs/administrator-playbook.md owns publication decisions.

Recommended package
1. A permanent garment identity label with piece number/name/artist, a tamper-evident serialised holographic feature, and a concealed secure NFC tag.
2. An artist-signed certificate carrying the same immutable piece/certificate identifier, material/technique, actual measurements, creation date, distinguishing details and photographs/reference to a preserved photographic record.
3. A matching premium ownership card and Hewge provenance record. Keep the original artist certificate with the garment when it transfers; update the registration/card without forging or reproducing the artist's handwritten signature.

Credit the actual artist, designer and producer, with roles combined where appropriate. Agree credits and reveal timing in the release record, including identification on the certificate and accompanying material. The artist signs the certificate. Check contributor and print-template limits in docs/launch-readiness.txt.

There is no single universal world art authentication certificate or hologram. Authentication depends on the issuer, artist/recognised expert, supporting evidence and provenance. ICOM Object ID is internationally recognised for describing and identifying cultural objects; it is not an authenticity accreditation or proof of legal ownership. Use its nine descriptive categories plus photographs, short description and securely retained documentation. Never display an ICOM endorsement or claim certification merely for following the checklist.

What 'only Hewge can decrypt' should mean
Use a secure cryptographic NFC chip, such as NXP NTAG 424 DNA, with unique per-tag AES keys. On tap, an NFC phone opens a URL containing authenticated dynamic data. A Hewge-controlled server verifies the message authentication code, checks the tag/counter and revocation state, and returns a scoped verification result. Keep keys outside Git, the frontend, QR codes and public endpoints; use controlled provisioning and AWS KMS-protected secret storage or a suitable secure key service. Restrict service roles and audit provisioning/replacement. The tag also holds its key; the real security claim is that the reader never receives it, not that no device except Hewge possesses a key.

A public QR URL can open the registry and a hologram can help visual/tamper inspection. Neither can produce a fresh cryptographic proof. Encrypting a fixed printed string still permits copying that string. Do not build a custom cipher or treat a static NFC UID as secure authentication.

Limits to test before manufacture
- A genuine tag can be transplanted to a counterfeit; cryptographic tag verification alone cannot prove the surrounding garment authentic.
- The chip's certification does not certify the garment, the completed label or art-world acceptance.
- Challenge/counter handling must cover replay, repeated browser requests, replayed old links, forwarding and parallel scans without making false authenticity claims.
- TagTamper detects its tamper loop; its usefulness depends on the actual sewn attachment/encapsulation. A chip datasheet is not a washable garment certification.
- Obtain supplier samples, test NFC readability through the chosen fabric, repeated washing/dry cleaning/ironing as appropriate, flexing, seam removal and tag replacement. Do not apply a standard adhesive security sticker directly to delicate fabric and assume durability.
- Record close-up photographs of seams, print alignment, signature, seal and unique garment features. Define lost certificate/tag, damaged label, theft/dispute and revocation procedures.
- Back up/export provenance and preserve verification continuity if hosting or key infrastructure changes. Public exports must omit owner identities/evidence unless consented.

Verifier implementation
The server implements encrypted SUN verification, AES-CMAC checked against published vectors, UID binding and an atomic monotonic counter check together with the piece verification hold. /verify consumes a fresh URL fragment only on an explicit button press. NFC is disabled until real hardware commissioning is complete; do not sell a garment as NFC-authenticated before that integration and testing. Successful verification identifies the registered chip, not legal title or the surrounding garment.

Commissioning profile
Have the encoder/supplier use NTAG 424 DNA file 02 with encrypted PICC data, mirrored UID and read counter, encrypted PICC field e (32 hex characters), and truncated MAC field c (16 hex characters). This verifier uses SDMMACInputOffset == SDMMACOffset (empty application MAC input); other profiles require a corresponding reviewed verifier change. Program NDEF as https://hewge.design/verify#tag=<UUID>&e=<dynamic PICC>&c=<dynamic MAC>. Calculate offsets against actual NDEF bytes, including the URI prefix; do not copy offsets from another URL. Set distinct random per-chip SDMMetaRead and SDMFileRead AES-128 keys, replace factory admin/write keys, lock unauthenticated configuration writes, and keep programmer/admin keys separately offline. Never reuse keys for a backup tag. The phone does not receive keys.

Register the keys after secure programming with:
AWS_PROFILE=hewge npx tsx scripts/provision-tag.ts --piece <piece-id> --uid <UID> --keys /private/tag-keys.json --tag <the-UUID-programmed-in-NDEF>
The file must be owner-readable only (chmod 600) and contain {"meta":"32 hex digits","file":"32 hex digits"}. Never pass secrets in command arguments or commit the file. Registration encrypts with the retained NFC KMS key and encryption context bound to piece/tag, records the UID uniquely, and leaves the tag provisioned/inactive. It does not program hardware. Archive programmer keys under controlled encrypted custody, then remove working plaintext files safely.

Use the studio Authenticity tab to commission up to two distinct tags before dispatch, with a fresh tap, physical inspection and artist certificate evidence. This consumes that tap. Test subsequent taps on iPhone/Android, repeat/replayed links, tampering, wash/flex durability and removal/transplant scenarios. Enable public verification only after commissioning with the nfcCommissioned=true deployment context; the flag is an operator assertion, not proof of a wash test. Replacement tags are activated only through a reviewed recovery case, with a fresh e/c proof and revocation of replaced tag IDs.

Damage, loss and certificates
The permanent piece identity and provenance survive tag failure. The verified owner can open a recovery case from their collection; this freezes verification/transfers. Hewge checks physical characteristics and stored photographs, the artist's record/signature, original sale evidence and registered ownership. A printed code, spare tag or unsigned certificate alone is insufficient. Keep one artist-signed paper certificate and an archived photographic copy. The certificate has a version; reissue requires a new artist signature and a permanent recovery event. Do not silently overwrite the original record. A second independently keyed chip is optional redundancy, not an extra transferable bearer title. If account access is also lost, a reviewed account recovery precedes a transfer.

Blockchain
No token/blockchain is required for this architecture. A timestamped hash or NFT cannot establish physical authenticity or repair a damaged tag on its own. Do not equate token control with legal garment ownership. Independent signed exports/checkpoints could add external evidence later without replacing physical inspection or the privacy-preserving registry. See docs/permanent-provenance.txt for archive continuity and recovery drills.
