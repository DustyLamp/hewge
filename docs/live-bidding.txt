HEWGE — LIVE BIDDING AND PRIVATE REHEARSALS

Scope alignment — 17 October 2026
This is the garment-auction implementation, not a book sales or collaborator-selection system. Each piece has individually chosen dates and an administrator-designed reveal plan within the current gates; one real auction is open at a time and the highest valid bid wins. Influential relationships and social proof do not confer bidding preference. See docs/administrator-playbook.md for the intended experience and known gaps. The annual book has a separate publication/purchase process still to develop.

The studio's Rehearsal tab creates a five-minute private copy of a piece's
presentation. Sign in with the studio authenticator, select After Hours and
start a session. Place a simulated bid, simulate another collector, then close
the rehearsal or let its deadline pass. Recent sessions reopen from the selector.
Only the studio identity that created a session may read it, bid or close it.
A second tab needs its own studio sign-in. There is no public rehearsal toggle.
Rehearsals cannot take payment, enter the public release directory, create an
owner, send winner emails or enter the real settlement worker. They retain an
audited history; a fresh session gets a new identifier instead of resetting one.
They do not test Stripe, delivery eligibility or legal consent in the real world.

AUTHORITY AND TRANSPORT

HTTPS bid commands go to Lambda in Stockholm. DynamoDB strongly reads the
auction. Conditional transaction writes require the expected revision, an open
status and server-evaluated opening/closing time. The bid receipt, auction head,
bidder state and audit event are committed atomically. The shared bid engine is
used by both real bids and simulations; real bids additionally require the live
launch gate, verified account/card, size/country eligibility and versioned terms.
The seller cannot bid on a real piece.

The browser keeps a stable request ID until an uncertain bid is reconciled. A
repeated matching request returns its original receipt. An event, spinner or
button press is never an accepted bid. Concurrent bids do not silently become a
higher bid: a stale submission is rejected and the collector must review again.

DynamoDB Streams triggers a separate publisher after committed head changes.
AWS AppSync Events manages WebSocket fan-out. The browser receives revision
notifications, then fetches an authorised strong snapshot. No bidder identities,
prices, artwork or unrevealed fields travel through the socket. Only the
publisher's IAM role can publish. Lambda authorization limits each subscriber
to its exact channel, rejects wildcard subscriptions and checks public release
publication. Private opaque tickets expire after four minutes, are hashed in
DynamoDB, and can only be issued through an authenticated MFA studio session.
Existing sockets could receive revision-only signals until closed; every private
snapshot still requires current studio MFA. Tickets are not stored in URLs.

Clients resynchronise after subscription, reconnect, returning to a visible tab,
accepted bids and opening/closing boundaries. They coalesce event bursts, reject
older revisions, renew connections, use heartbeat detection and exponential
reconnect backoff with jitter. Polling continues with jitter/backoff if sockets
fail. Hidden/offline tabs pause. Bidding waits when snapshots fail or become
stale. Public bid history contains only ten recent amounts, ordered sequences
and server timestamps. Personal highest-bid status requires account authentication.

TIME, CAPACITY AND FAILURES

One Stockholm write authority orders each piece by transaction revision and bid
sequence, not client clocks or event arrival time. Display countdowns use server
UTC plus monotonic elapsed time. A device clock cannot extend an auction.
The audit writer rechecks the deadline after writing its locked intent and before
submitting the transaction. DynamoDB has no built-in commit-time wall-clock
predicate: this is server validation immediately before submission, not a promise
of zero clock error or exact physical commit at a millisecond boundary. There is
no automatic last-second extension. The existing minute worker settles the
highest accepted bid; clients may show closed before settlement completes.

The deployment is pay-per-use: API Gateway HTTP, Lambda, DynamoDB on-demand,
AppSync Events, S3 and a small failure queue. No always-on socket server or NAT.
The HTTP stage allows up to 1,000 requests/second, bursting to 2,000, subject to
account/service quotas. Application mutation rate limits remain in place.
Managed fan-out scales independently of bid acceptance. Snapshot reads still
scale with viewers and events, and a popular single piece serializes writes to
one head/audit chain. This deployment has NOT been certified for millions of
simultaneous bidders. Load-test the anticipated audience, monitor throttling and
latency, and raise quotas or add a versioned public snapshot cache before a large
launch. Cost is usage-dependent, not guaranteed free.

Publisher failures retry with partial-batch reporting and a 14-day SQS failure
queue. Iterator lag and queued failures have CloudWatch alarms; external alarm
notification subscriptions are not configured by this change. The browser's
snapshot recovery works independently of the publisher. The durable auction
and audit records are the recovery source, not the socket or the queue.
DynamoDB/PITR, daily backups and protected audit archives retain their existing
encryption and retention settings. Regional failure pauses bidding/settlement;
there is no second-region write failover and no DSQL requirement for this design.

CHECKS AND LAUNCH

Unit tests cover shared bid conditions, competing simulations, duplicate/late
receipts, private authorization, channel isolation, public redaction and socket
reconnect/renewal. scripts/smoke-bidding.mjs verifies real AWS MFA, WebSockets,
concurrency, replay and public launch isolation using a disposable synthetic
identity. Its operational fixtures are removed; protected synthetic audit events
remain. The rehearsal is not evidence that live card charging is ready.

Checkout remains disabled until the existing README payment, artist, sizing,
seller, shipping, returns, tax, privacy and sandbox launch requirements are met.
Pushes run CI. The current Amplify branch uses an explicit deploy command; a git
push by itself does not publish the site.
